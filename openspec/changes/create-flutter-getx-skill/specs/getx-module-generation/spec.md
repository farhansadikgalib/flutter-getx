# Spec Delta

## Purpose

Defines how a feature module is added to a scaffolded project: generated with get_cli where possible, conformed to the project's base classes, and registered in the route table so it is navigable immediately.

## ADDED Requirements

### Requirement: get_cli is available before module generation
The skill SHALL verify that the `get` command runs and reports its version before using it, and SHALL activate or re-activate `get_cli` from pub when it is missing or broken.

#### Scenario: Stale global activation
- **WHEN** `get --version` fails with a kernel binary or snapshot error
- **THEN** the skill runs `dart pub global activate get_cli` and re-checks before proceeding

#### Scenario: get_cli unavailable
- **WHEN** activation fails (offline or incompatible SDK)
- **THEN** the skill falls back to generating the module files from its bundled templates and tells the user get_cli was not used

### Requirement: New module follows the page layout
Adding a module named `<name>` SHALL produce `lib/app/modules/<name>/bindings/<name>_binding.dart`, `controllers/<name>_controller.dart`, and `views/<name>_view.dart`, and SHALL add a route constant and a `GetPage` entry to the route table.

#### Scenario: Generate a profile module
- **WHEN** the user asks to add a "profile" screen
- **THEN** the three files exist, `Routes.PROFILE` resolves to `/profile`, and `AppPages.routes` contains a page bound to the profile binding

#### Scenario: Nested module
- **WHEN** the user asks to add "settings" inside the "profile" module
- **THEN** the files are created under `modules/profile/settings/` and the route is registered

### Requirement: Generated module conforms to base classes
After generation, the module's controller SHALL extend the project's base controller and the view SHALL extend the project's base view, implementing its required app bar and body members, so that page state and the connection banner work without extra code.

#### Scenario: Post-processing applied
- **WHEN** a module is generated with get_cli
- **THEN** the controller no longer extends `GetxController` directly and the view no longer extends `GetView` directly, and `flutter analyze` passes

### Requirement: Supporting artifacts are generated on request
The skill SHALL support adding a model from a JSON sample, locale keys from `assets/locales/*.json` (`get generate locales`), and a remote data source that uses the project's safe API client. Because `get generate model` crashes on Dart 3 projects in get_cli 1.9.1, models SHALL be generated by the skill's bundled JSON-to-model script.

#### Scenario: Model from JSON sample
- **WHEN** the user supplies a JSON sample and asks for a model
- **THEN** a Dart model with `fromJson`/`toJson` is created under `lib/app/data/models/` (or a chosen folder) and compiles, and nested objects become their own classes

#### Scenario: Locale keys
- **WHEN** new strings are added to `assets/locales/en_US.json` and `ar_AR.json`
- **THEN** running the locale generator updates the translation keys and both locales stay in sync

### Requirement: Module generation is idempotent and safe
Re-running module generation for an existing module SHALL NOT overwrite user-edited files; the skill SHALL report that the module exists and stop.

#### Scenario: Duplicate module
- **WHEN** the user asks to add a "home" module that already exists
- **THEN** no files are changed and the user is told the module already exists
